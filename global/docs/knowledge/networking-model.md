# 网络排障的分层模型

> 一次访问要过好几道门，每道门属于**不同设备**、由**不同配置**管。排障第一步永远是：确定卡在哪一道。

## 三道门

```
手机 ──▶ 运营商 ──▶ 光猫 ──▶ 路由器 ──▶ 目标主机
                    (1)       (2)        (3)
```

| # | 谁 | 管什么 | 配置在哪 |
| --- | --- | --- | --- |
| 1 | 光猫 | 运营商 → 内网的转发 | 运营商定制 UI，`user` 账号常常改不了 |
| 2 | 路由器 | WAN → LAN 的转发 / NAT | IPv4：端口映射页；**IPv6：`ip6tables`，很多机型没有 UI** |
| 3 | 目标主机 | 包到了之后收不收 | 主机自己的防火墙（ufw / firewalld / 厂商组件） |

**外层的门不放行，内层开多大都没用。** 所以定位顺序是**从外往里**，一次只动一道门，动完立刻验。

## IPv4 和 IPv6 的关键差别（最容易混）

端口号是同一套（0–65535）。分开的是**地址与规则**：

|  | IPv4 | IPv6 |
| --- | --- | --- |
| 内网地址 | 私有，需要 NAT | **每台设备一个公网地址** |
| 路由器要做的事 | 地址转换（DNAT） | 只做路由转发 |
| 于是需要 | **端口映射 / 虚拟服务器 / DMZ** | **防火墙放行**（无"映射"这个概念） |
| 内核规则表 | `iptables` | `ip6tables`（完全独立的表） |

→ 「v4 上开了 5666」和「v6 上开了 5666」是**两件独立的事**，不会互相生效。

## 防火墙关不关 ≠ 端口通不通

两件正交的事：

- **防火墙**决定"包到了本机，内核收不收"
- **端口通不通**还取决于有没有进程在听（`ss -lnt` / `lsof -nP -iTCP:PORT -sTCP:LISTEN`）

监听形态有三类：只绑 `0.0.0.0`（只 v4）／只绑 `[::]` 且 `bindv6only=0`（双栈，一个 socket 通吃）／两边各绑一个 socket。

## 怎么定位卡在哪一道

| 手段 | 能回答 |
| --- | --- |
| 从外部探端口（在线工具 / 手机流量） | 整条链路通不通 |
| 在中间设备上挂 **计数器** | 包有没有到达这一跳 |
| `tcpdump` | 包到了谁手里、谁回的拒绝 |
| `ip -6 route get <dst>` / `netstat -rn` | 路由对不对、下一跳是谁 |
| `ip6tables -S` / `nft list ruleset` | 这一层有没有拒绝规则 |

**计数器法**（不改行为，纯观测）：

```bash
ip6tables -t mangle -A PREROUTING -p tcp --dport 5666 -j RETURN
ip6tables -t mangle -vnL PREROUTING        # 看 pkts 有没有涨
```

## 两条纪律

**1. 先校准工具，再相信结果。**
打一个已知结果的靶子，确认工具能区分「通 / 拒绝 / 超时」。踩过的坑：`ipv6-test.com/json/webserver.php` 的 `url` 里写端口**无效**，它永远只连 80 —— 我曾据此断定"包没进来"，方向错了两次。

**2. 能在链路上打点，就别靠推理。**
错误码和超时是间接信号，很容易编出一个自洽但错误的故事。`iptables` 计数器 + `tcpdump` 才是直接证据。
