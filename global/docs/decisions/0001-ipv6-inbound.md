# 决策：IPv6 入站先走「路由器临时放行」，不追求持久化

> 生效中 · 2026-11-11 · 落地 `NX15000` 的 `forwarding_wan_rule` · 事实见 [../knowledge/ipv6-inbound.md](../knowledge/ipv6-inbound.md)

## 矛盾

要从公网访问家里的 NAS，但：

1. 边界是 ISP 之外的 **H3C NX15000**，它的 IPv6 入站被硬编码 `zone_wan_dest_REJECT` 挡着，**UI 里没有这个开关**；
2. 只能靠 `/debug.asp` 开 **telnet 15000** 进 `debugshell` 改 `ip6tables`；
3. 而该固件的 `/` 是 `overlayfs:/tmp/root`（**upper 在内存**），**任何 `/etc` 改动重启即失**，厂商配置 `/mnt/cfg/startup` 里也没有 IPv6 防火墙字段；
4. 同时 NAS 的 80 只是 `302 → :5666`，"看起来通了"很容易是假象。

## 处理

路由器只加**一条**全放行（`-d ::71e/… -j ACCEPT`），**接受重启后手动重放**；细粒度的端口白名单下移到 **NAS 自己的 XDP 防火墙**（它持久、有 UI）。命令固化到 [../examples/h3c-ipv6-allow.sh](../examples/h3c-ipv6-allow.sh)。

## 为什么

| 方案 | 成本 | 落选原因 |
| --- | --- | --- |
| **A. 路由器临时放行**（采用） | 零 | —— |
| B. 换 OpenWrt / 能管 IPv6 防火墙的路由器 | 硬件 + 迁移 | 一次性投入大，且当前需求是"偶尔访问" |
| C. 隧道（Tailscale / Cloudflare Tunnel） | 每台设备装客户端 | 更稳，但引入第三方依赖；留作备选 |
| D. NAS 直连光猫 LAN，绕过路由器 | 一根网线 | 会脱离现有内网管控，且 NAS 换网段影响面大 |

选 A 的理由：**零成本、不改拓扑、立刻可用**；而且这次已经把所有命令与坑固化成文档，重放的边际成本很低。

## 代价

1. **重启即失效**，容易忘 → 表现成"怎么又坏了"。
2. 为了改规则，**NX15000 的 telnet(15000) 要一直开着**，而该端口**无需密码即为 root** → 局域网内任何人都能提权。
3. 端口暴露面取决于 NAS 侧白名单；路由器这条不设限，**NAS 防火墙一旦被关掉就等于全裸**。
4. 前缀会变，**没有 DDNS 就会失效**。

## 复查条件

| 触发 | 动作 |
| --- | --- |
| 路由器重启频率 ≥ 每月 1 次 | 换成 C（隧道），彻底免维护 |
| 需要对外提供长期稳定服务 | 换成 C，或 B（换设备） |
| 局域网出现不可信设备 / 有访客长期接入 | **立刻关 telnet**，规则改为只能通过隧道下发 |
| 需要放的端口超过 5 个 | 重新评估：说明场景已从"偶尔访问"变成"对外服务" |
| NAS 防火墙被关闭 / 改回"默认允许" | 立刻收回路由器的全放行，改回按端口白名单 |

执行回退：`ip6tables -D forwarding_wan_rule <对应规则>`，或直接重启路由器（规则自然清空）。
